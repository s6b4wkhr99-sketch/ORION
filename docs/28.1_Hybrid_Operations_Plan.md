## 1. Executive Summary

CIOS는 Customer Intelligence 분석을 완료했으며, 현재 약 **645,000+** 고객이 적재되어 있습니다. 목표 Universe는 **2.4M**입니다.

Volume 28은 Enterprise 아키텍처 전환을 제안했고, v1.0.1 개발 과정에서 **UploadRollup 기반 대시보드 최적화**가 검증되었습니다 (State Intelligence: 3분+ → **~1초**).

**Volume 28.1**은 두 접근의 **장점만** 결합한 운영 확정안입니다.

| 출처 | 채택하는 장점 |
|------|--------------|
| **As-Built (v1.0.1)** | `UploadRollup` Summary Engine, SQL 집계, Top-N ZIP, async upload worker, 프론트 중복 fetch 제거 |
| **Volume 28** | Dashboard 고객 단위 조회 금지, SQL pagination, storage 정책, cache, index, async export |

**채택하지 않는 항목 (당장):** 별도 Analytics DB, 전면 monthly partitioning, batch 10K 일괄 전환, MV/Rollup 이중 집계

## 2. Operating Architecture

### 2.1 Data Flow (확정)

```
Customer Upload
      │
      ▼
OLTP Database (Customer / Customer Intelligence / Raw Upload)
      │
      ▼
Intelligence Engine (batch: 100 flush / 1000 commit)
      │
      ▼
UploadRollup  ← Primary Summary Engine (upload 단위)
      │
      ├─► Materialized Views  ← Global / cross-upload 보조 (Phase B)
      │
      ├─► Dashboard Cache (15 min, upload 완료 시 invalidate)
      │
      ▼
Dashboard APIs (summary only)
      │
      ▼
Customer Drilldown (paginated SQL only, 100 rows/page)
```

### 2.2 Layer Responsibilities

| Layer | 역할 | 기술 |
|-------|------|------|
| **Write** | 업로드·분석·rollup 생성 | async worker, batch commit, bulk mode (대용량) |
| **Read (Dashboard)** | KPI·지도·세그먼트·Top ZIP | `UploadRollup` → MV → cache 순 |
| **Drilldown** | 고객 그리드·검색·상세 | SQL `LIMIT/OFFSET` + index |

### 2.3 Golden Rules (운영 필수)

1. **Dashboard는 고객 레코드를 직접 분석하지 않는다.**
2. **집계는 PostgreSQL에서 수행한다.** Python full load 금지.
3. **ZIP은 Top-N만 반환한다.** (기본 50, 최대 500)
4. **고객 API는 server-side pagination만 사용한다.** (기본 100 rows)
5. **Export는 비동기 + streaming이다.**
6. **Raw JSON은 오류 건만 저장한다.** (정상 건은 intelligence summary만)
7. **Upload 완료 시 rollup rebuild + cache invalidate.**

## 4. Seven Operating Principles

| # | Principle | As-Built | Volume 28 | Hybrid Rule |
|---|-----------|----------|-----------|-------------|
| 1 | No full customer memory load | State rollup ✅ | 금지 규칙 | **전 대시보드 rollup/MV only** |
| 2 | SQL aggregation | State ✅ | PostgreSQL GROUP BY | **모든 dashboard query** |
| 3 | Top-N ZIP | 150건 ✅ | 50/100/250/500 | **기본 50, UI 확장 100/250** |
| 4 | Server pagination | Gap ❌ | 100 rows | **Customer API SQL pagination** |
| 5 | Batch analysis | 100/1000 ✅ | 5K–10K | **현 설정 유지, 점진 증가** |
| 6 | Dashboard cache | 없음 | 15 min | **15 min + upload invalidate** |
| 7 | Storage policy | 부분 | JSON/Export/Temp | **오류만 JSON, Export 14일 삭제** |

## 5. What We Do NOT Do (Now)

| Excluded | Reason |
|----------|--------|
| Separate Analytics Read-Only DB | MV + cache로 충분; 2.4M 이후 검토 |
| Full monthly partitioning (customers) | audit/log부터; customer 테이블은 Phase C |
| MV + Rollup duplicate aggregation | 역할 분리: Rollup=per-upload, MV=global |
| Dashboard full rewrite | rollup 경로 확장이 더 빠르고 검증됨 |
| Batch 10K immediate switch | 100/1000 안정성 확인 후 점진 증가 |
| Store every customer raw JSON | storage 100GB+ 주원인 |

## 7. Storage Policy (확정)

| Data Type | Store Where | Retention | Rule |
|-----------|-------------|-----------|------|
| Upload original (Excel/CSV) | `uploads/YYYY/MM/` (filesystem) | Until archive | DB: path + checksum only |
| Processed archive | GZIP on disk | 90 days → delete | Phase B |
| Raw JSON per row | PostgreSQL | — | **Errors/failures only** |
| Intelligence summary | `customer_intelligence` columns | Permanent | Always |
| Full trace | `intelligence_trace` table | 90 days → archive | Bulk mode: skip |
| Export CSV | `uploads/exports/` | **14 days → delete** | Phase A |
| Temp files | `/tmp/uploads`, `/tmp/export` | **24h → delete** | Daily cleanup |
| Campaign targets | `campaign_id` + `customer_id` only | Permanent | No full profile duplicate |

## 8. API & Dashboard Contract

### 8.1 Dashboard APIs (summary only)

| Endpoint | Data Source | Max Rows |
|----------|-------------|----------|
| `/dashboard/executive` | Rollup + MV + cache | aggregated |
| `/dashboard/state` | Rollup + cache | ZIP Top-N (default 50) |
| `/dashboard/zip` | Rollup (scoped) | single ZIP summary |
| `/dashboard/product` | Rollup | per-product aggregate |
| `/dashboard/roi` | MV / campaign tables | aggregated |

### 8.2 Customer APIs (paginated only)

```
GET /customers?page=1&limit=100&state=CA&upload_id=...
```

- **Prohibited:** return all customers in one response
- **Required:** SQL `COUNT(*)` + `OFFSET/LIMIT`
- Index filters pushed to SQL WHERE clause

### 8.3 Export APIs (async)

```
POST /export          → 202 Accepted, job_id
GET  /export/{id}     → status
GET  /export/{id}/download → streaming FileResponse
```

## 10. Acceptance Criteria (Volume 28.1)

### Performance
- [ ] All dashboards < 2 sec @ 645K
- [ ] All dashboards < 5 sec @ 2.4M
- [ ] Customer search < 500 ms
- [ ] Export is async and non-blocking
- [ ] Upload uses batch worker (no UI freeze)

### Storage
- [ ] Database < 60GB after cleanup (target 40GB)
- [ ] No raw JSON on successful import rows
- [ ] Uploads stored on filesystem, not in DB BLOB
- [ ] Exports auto-expire after 14 days
- [ ] Temp files cleaned daily

### Architecture
- [ ] No dashboard code calls `Customer.all()` or equivalent full scan
- [ ] Dashboard reads `UploadRollup` or MV only
- [ ] Customer pages use server-side pagination (100 rows)
- [ ] Upload completion triggers rollup rebuild + cache invalidation
- [ ] Platform ready for growth beyond 2.4M (rollup + MV + cache)
